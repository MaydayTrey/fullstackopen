Observation - Re-rendering whole components based on one component changing is a bit wild. React re-runs the component functions and produces a new tree of plain objects, then diffs that against the previous one and updates only the DOM nodes that actually differ. DOM operations are expensive, functions are not. At scale this becomes a problem, if there were thousands of rows, an expensive calculation as a result, deep tree re-rendering. But there are circumnavigations, React.memo will wrap a component so it skips re-rendering when its props haven't changed by identity, useMemo caches an expensive calculation between renders. useCallback keeps a function identity stable so memorized child elements don't re-render pointlessly. 
Vanilla gives you precise minimal updates at the cost of manually keeping data and DOM in sync. React gives you guaranteed correctness at the cost of some wasted computation. 
Solid and Svelte update only what changed without re-running components.

Looks like we're going to return to learning about Promises here;
A Promise is an object representing the eventual completion or failure of an async operation. 

A promise represents an asynchronous operation - what I remember is essentially this is an object which has certain properties, and based on those, it will tell you when it's fulfilled, if it does get fulfilled - and it either tells you pending, success, or failure. 

3 Distinct States:
Pending - async op for the promise has not yet finished, and so the final value is not yet available.
Fulfilled - the operation has completed
Rejected - An error prevented the final value from being determined. 

To access the result of the operation represented by the promise, you must register an event handler to the promise - this is achieved using the method then:

})

What the hell is a RESTful API - REST API? 
REST is a convention for building HTTP APIs. It's a set of agreed-upon conventions for how URLs and HTTP methods should map to operations on data. 
The core idea is data is organized into resources, each with its own URL, and you act on them using HTTP methods that already exist. 
Resources get URLs - /persons (whole collection) --> /persons/3 (one specific person)
URL names a thing, its noun, not an action or verb. 
GET -> /persons -> Fetch all of them
GET -> /persons/3 -> fetch that one
POST -> /persons -> Create a new one
PUT -> /persons/3 -> Replace that one entirely
PATCH -> /persons/3 -> Update part of that one
DELETE -> /persons/3 -> Remove that one

This literally seems like common sense. Nouns for resources, HTTP methods for verbs. Collections versus singulars. POST to the collection to create. 
Statelessness - Every request carries 
JSON-Server requires all data to be sent in JSON format. What that means in practice is that the data must be a correctly formatted string, and that the request must contain the Content-Type request header with the value application/json

SIDE-LESSON; I'm repeatedly struggling with just letting handlers change state, and I keep trying to do logic or computation on them. In Vanilla JS the handler is the renderer. 
button.addEventListener('click', () => {
  document.querySelector('#out').textContent = anecdotes[randomIndex()]
})

A click produces output, directly in the handler, it's how I've written logic thus-far. React splits it into two phases. 
Where would the output go? 
React call the handler and throws away the return value. The only thing producing output is return on a component function. A handler cannot then alter the DOM, it must only alter state which reflects the change in a JSX output. If it needs to be true after the click is finished, then the handler cannot be the carrier of it, Handlers run once and vanish. State is the only thing surviving between rendering. 
Vanilla JS: Click -> Compute -> Write to screen
React: Click -> Change data; Separately: State --> Render to Screen 
When writing a handler ask yourself, what piece of data is different now. Call that setter. Stop. No return value.
